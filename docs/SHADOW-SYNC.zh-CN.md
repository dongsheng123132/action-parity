# 影核协议（ActionParity ShadowCore Profile）

**状态：** ActionParity 影子与同步子规范 0.1（非规范性草案）
**线上标识：** `action-parity/sync@0.1`
**适用范围：** Windows、macOS、iOS、Android、鸿蒙、Linux、Web、CLI/TUI 与远程 Agent
**English:** [ActionParity ShadowCore Profile](SHADOW-SYNC.md)

**原则：一核多影 / One Core, Many Shadows**

> 一个产品只有一个权威动作核心。所有界面——Windows 窗口、手机屏幕、终端、
> MCP 工具、测试夹具——都是它的原生影子，投影同一套 Action、State、Event 和
> Policy。设备之间同步的是动作、状态和事件，不是屏幕。

由此得到三个结果，这也是采用影核协议的理由。

1. **每个平台都原生，但行为不分叉。** 各端画自己的控件，谁也不再实现一遍
   业务规则。
2. **远程操作不传像素。** 影子端凭不透明游标续传，收到的是一小段有序增量，
   而不是一帧帧画面。
3. **机器可验证。** 每个有业务意义的动作都能无界面调用、无界面断言，所以 AI
   可以把整个产品——包括远程和多设备路径——完整测一遍，不需要截图、不需要
   鼠标坐标、不需要视觉模型。见 [§10 机器验证](#10-机器验证)。

影核协议**不是**：不是所有平台跑同一个二进制，不是共用一套控件库，也不是
远程桌面。

## 1. 必须先说清的区别

“GUI 是影子”是一句有用的架构判断，前提是**影子**指“把权威语义用原生控件投影
出来”。如果它被理解成“所有平台共用同一批像素、控件或同一个可执行文件”，那就
是错的。

iOS 沙箱、Windows 服务、macOS 授权、鸿蒙 Ability、设备传感器和后台执行规则
本来就不同。符合本协议的产品按以下优先级共享实现：

1. 一个权威动作核心，通过本地或远程 IPC 调用；
2. 一个可移植核心库，为多个平台分别编译；
3. 由同一份契约生成的多个独立实现，并用一致性测试证明等价。

共享的不变量是语义，不是二进制：

```text
                  版本化 Action 契约
                          │
                    规范 State 模型
                          │
                  只追加 Event 流
                          │
                  Policy / 权限闸门
                          │
        ┌──────────────┬───┴────────┬──────────────┐
        │              │            │              │
   Windows GUI     macOS GUI     iOS GUI      鸿蒙 GUI
        │              │            │              │
        └──────────── 原生影子 ─────────────────────┘
                          │
                  CLI / TUI / MCP / AI
```

## 2. 四个共享层

### 2.1 Actions（动作）

每个有意义的操作都有稳定 Action ID、带类型的输入输出、副作用等级、超时、
权限要求和幂等语义。各界面收集输入的方式可以不同，但调用的是同一个动作身份。

### 2.2 State（状态）

State 是规范化的领域数据，不是序列化的界面树。每个界面只投影自己需要的字段。
手机可以显示一张紧凑任务卡，Windows 桌面显示多栏检查器；两者是同一份任务状态
和同一个状态版本的不同视图。

### 2.3 Events（事件）

每个被接受的动作和每次提交的状态变更都产生一条有序事件。有了事件才有重放、
审计、离线恢复、调试和增量同步。事件里放大对象的引用，不要把大对象塞进事件。

### 2.4 Policy（权限）

权限在所有影子之下强制执行。远程手机、CLI 或 AI Agent 不能因为绕开了桌面按钮
就获得更大权力。破坏性、涉及金钱、涉及特权或对外可见的动作，其确认、审计、
取消和脱敏要求都留在动作核心里。

## 3. 同步差量，而不是同步屏幕

远程影子应当交换结构化命令和差量：

```text
手机影子                      Relay                    Owner 节点
     │ sync.hello(cursor=41)    │                        │
     ├─────────────────────────>│                        │
     │                          ├── 请求 41 之后 ───────>│
     │<──── sync.delta(42..47) ─┤                        │
     │ 渲染原生卡片              │                        │
     │                          │                        │
     │ sync.command(task.pause, idempotency=k9)          │
     ├─────────────────────────>├───────────────────────>│
     │                          │            执行 + 鉴权 │
     │<──── 结果 + 事件 48 ─────┤<───────────────────────┤
```

正常情况下只传输命令信封、小体积事件载荷和可选的内容寻址大对象引用。它不会
持续传输：

- 截图；
- 远程帧缓冲；
- 完整数据库；
- 每次变更后的完整状态快照；
- 平台专有的视图树。

对表单、任务列表、日志、进度、设置和 Agent 工作来说，这能把带宽降低几个数量
级，并且各端保持原生。像素流仍然适用于视频、游戏、任意遗留应用，以及语义尚未
被抽取出来的画布类界面。

## 4. 传输无关的同步信封

草案 Schema 是
[`schema/action-parity-sync.schema.json`](../schema/action-parity-sync.schema.json)，
可以承载在 WebSocket、SSE + HTTP、QUIC、本地 IPC、消息队列或产品已有的 relay 上。

信封必须表达的概念：

| 概念 | 用途 |
|---|---|
| `stream_id` | 稳定的逻辑状态/事件流 |
| `message_id` | 去重与追踪 |
| `cursor` | 影子确认过的不透明续传位置 |
| `state_version` | 乐观并发与陈旧写检测 |
| `execution_id` | 关联命令、生命周期、结果和审计 |
| `idempotency_key` | 让重连后的命令重试安全 |
| `actor` | 标识设备、用户、服务或 Agent |
| `events` | 游标之后的有序状态增量 |

[ClawMe 任务差量样例](../examples/sync/clawme-task-delta.json)展示了最小可用的
事件批次。

确认写动作的样例覆盖成功与设备状态陈旧两种结果：

- [`sync.command`](../examples/sync/clawme-attention-decision-command.json)；
- [`sync.result`](../examples/sync/clawme-attention-decision-result.json)；
- [`sync.conflict`](../examples/sync/clawme-attention-decision-conflict.json)。

## 5. 消息角色

首版协议使用八种角色：

| 类型 | 方向 | 含义 |
|---|---|---|
| `sync.hello` | 影子 → owner/relay | 协商 profile、能力和续传游标 |
| `sync.snapshot` | owner/relay → 影子 | 没有可用游标时给出基线状态 |
| `sync.delta` | owner/relay → 影子 | 已确认游标之后的有序事件 |
| `sync.challenge` | owner → 影子 | 把确认绑定到调用者、动作、输入摘要和状态版本 |
| `sync.command` | 影子 → owner | 携带权限与幂等信息调用一个动作 |
| `sync.result` | owner → 影子 | 按执行 ID 关联的结构化动作结果 |
| `sync.ack` | 影子 → owner/relay | 确认一个持久化游标 |
| `sync.conflict` | owner → 影子 | 拒绝陈旧或不兼容的状态假设 |

传输层可以加心跳和压缩帧，但不得改变动作语义，也不得让传输层数据成为新的事实
源。

## 6. 顺序、重试与离线行为

- 一条流必须有全序，或声明明确的分区策略。
- 游标对影子必须是不透明的。
- 相同幂等键的重复命令必须返回首次提交的结果，或一个稳定的“执行中”响应。
- 影子只能确认已经持久落到本地投影的状态。
- 依赖状态版本的命令应当携带 `expected_state_version`。
- owner 必须拒绝或显式合并陈旧写；“最后写入者获胜”不得成为未声明的默认行为。
- 重连的影子应当从最后一个持久游标请求增量。
- 没有变化时可以返回空增量和同一游标，让低成本轮询不必伪造状态变更。
- 历史被压缩时，owner 发送快照和新游标。
- 影子可以渲染乐观界面状态，但必须与提交结果和事件流对账。

### 6.1 可靠的远程写

远程写不是“把 JSON 发出去然后祈祷”。符合协议的 owner 在调用动作核心之前执行
这道闸门：

1. 认证设备，并对动作和资源做授权；
2. 签发短时效 `sync.challenge`，绑定调用者、Action ID、规范化输入摘要和当前
   状态版本；
3. 先查幂等键，再判过期；
4. 若该键已提交过同一请求，直接返回首次结果；
5. 若同一个键对应不同输入或不同执行身份，拒绝；
6. 拒绝过期命令，并把 `expected_state_version` 与权威状态比对；
7. 状态陈旧时返回 `sync.conflict`，不消费挑战，也不执行；
8. 校验并一次性消费匹配的确认挑战；
9. 在存储模型允许的前提下，原子提交业务效果、结果、事件和幂等记录。

信封中的 `confirmation` 只记录确认方式、挑战身份和时间。它不得包含生物特征
模板、设备密钥或可重放的凭证。确认的真实性由 owner 通过可信平台通道校验。

分布式传输通常提供至少一次投递，而不是魔法般的恰好一次执行。可观察的
“恰好一次”依赖幂等账本与业务效果处在同一个原子边界内；做不到时，动作本身必须
幂等，或者有明确的对账/补偿设计。

## 7. 能力协商

平台能力不同，所以 `sync.hello` 要声明该影子能渲染什么、能调用什么：

```json
{
  "surface": "ios",
  "actions": ["task.status", "task.pause", "approval.respond"],
  "features": ["push", "biometric_confirmation", "offline_projection"],
  "schema_versions": ["task@2", "approval@1"]
}
```

不支持的能力要写成明确的一致性例外或委托执行，而不是静默地假装支持。例如
iPhone 影子可以请求 Windows owner 节点执行 `workspace.build`，但不能假装自己在
本地跑了 Windows 工具链。

## 8. 安全与隐私

同步实现：

- 必须认证设备，并把每条命令绑定到调用者；
- 必须在 Action ID 和资源范围上授权；
- 必须在权威核心处强制确认；
- 必须在事件进入 relay 之前脱敏；
- 必须加密传输，并保护持久游标与令牌；
- 必须支持设备吊销；
- 必须把内容大对象与控制面事件分离；
- 应当把敏感文件与模型上下文留在 owner 节点；
- 应当发布从命令到结果再到状态事件的可审计链路。

relay 应当能够转发已加密或已脱敏的增量，而不持有用户的完整工作区。“只同步底层”
指的是同步影子所需的最小语义状态，不是把整台机器上传。

## 9. 参考产品映射

### 9.1 ClawMe

ClawMe 的边界本来就是对的：本地 owner agent、持久 relay、任务、命令、事件，以及
原生 iOS 客户端。它应当演进，而不是重写：

1. 给现有命令起稳定的 Action ID；
2. 给 task/attention/event schema 加版本；
3. 给 relay 加不透明游标和幂等键；
4. 让 iOS 界面成为任务与待办状态的投影层；
5. 按同一协议增加 macOS、Windows、Android 和鸿蒙影子；
6. 文件、工具执行和敏感上下文继续留在 owner 节点。

第一个竖切面应当是一条远程任务：
`task.status` → `task.events` → `task.pause/resume` → `approval.respond`。

### 9.2 UURescue

UURescue 已经有任务状态机、只追加事件日志、检查点和可恢复接班，很适合作为规范的
连续性运行时：

1. 把 `task.status` 和 `task.events` 暴露为只读动作；
2. 给每条事件分配稳定序号/游标；
3. 导出增量，而不是复制整个任务目录；
4. 增加需确认的 `checkpoint.create` 与 `takeover.start`；
5. 让手机/桌面影子投影同一份恢复状态；
6. 只把 ClawMe relay 当传输通道，不当第二个事实源。

```text
UURescue 连续性状态 ── 事件/增量 ── ClawMe relay
          │                            │
      owner 执行                    原生影子
```

## 10. 机器验证

做 GUI 软件最难的部分不是写出来，而是证明它还能用。驱动真实窗口慢、脆、还受
分辨率、语言、主题、焦点和动画影响；同时驱动多台设备更糟。于是团队恰恰没测那些
真正会在现场炸掉的路径：重连、陈旧写、重复命令、跨设备状态。

影核产品回答“软件有没有做对事情”并不需要视觉模型，只需要四层成本不同的测试。

| 层 | 回答什么问题 | 驱动方式 | 典型成本 |
|---|---|---|---|
| 动作核心契约 | 这个动作做对了吗？ | 直接调用或 `action run --json` | 毫秒级、确定性 |
| 绑定一致性 | 各界面调用的是同一个 Action ID 吗？ | 清单 + 界面自省 | 毫秒级、不需要窗口 |
| 同步一致性 | 重试、乱序、陈旧下远程路径对吗？ | 录制好的信封 fixture | 毫秒级、不需要第二台设备 |
| 真实 GUI 旅程 | 人能看到、够得着、看得懂吗？ | UI 自动化 / 无障碍 | 秒级、少量用例 |

只有最后一层需要真实窗口，而且它会缩小到真正只能靠窗口验证的部分：可达性、
焦点顺序、对比度、高 DPI 和标签。

### 10.1 想被机器验证，实现必须暴露什么

- 一份清单，列出 Action ID、输入输出 Schema、副作用和各界面绑定；
- 每个已声明动作都能无界面调用：stdout 输出稳定机器信封、stderr 输出诊断、
  退出码有意义；
- 每个 GUI 界面上有稳定的非视觉绑定标识（automation ID、`data-action-id`、
  无障碍 ID），让绑定检查不依赖像素；
- 带不透明游标的事件流，使“效果”可以断言成事件，而不是截图 diff；
- 沙箱或可指定的状态根目录，让测试永远不碰真实用户数据；
- 一套 `sync.*` 信封 fixture，覆盖续传、空增量、重复幂等键、过期挑战和陈旧
  `expected_state_version`。

### 10.2 Agent 可以无人值守跑的回路

```text
action list --json                 → 发现有哪些动作
action describe <id> --json        → 读契约，而不是读文档
action run <id> --json             → 在沙箱里执行
task.events --after <cursor>       → 断言已提交的效果
binding check <id>                 → 断言各界面都映射到该 Action ID
replay fixtures/sync/*.json        → 断言续传、重试和冲突规则
```

每一步都是文本进、文本出。Agent 可以在 CI 里跑、在裸机上跑、通过 SSH 跑，或者
在另一个 Agent 的工具回路里跑——不需要显示器、不需要驱动、不烧截图预算。

### 10.3 它不能证明什么

前三层全过，并不能证明人能用。它不能证明按钮可见、键盘可达、屏幕阅读器读得对、
200% 缩放下还看得清。这些仍然是真实 GUI 断言，符合协议的实现照样要发布它们。
本协议的主张更窄也更实用：**行为回归不再藏在 UI 自动化的抖动背后。**

### 10.4 用重放做调试原语

因为状态变更是有序事件，现场故障可以以“一段游标区间”的形式带回来，而不是一段
录屏。把这段区间对着动作核心重放，就能在开发机上复现缺陷，不需要设备、不需要
账号、不需要录屏。这也是影子证明自己没有编造状态的方式：给定同一份增量，它必须
得到同一份投影。

## 11. 对开发速度的影响

这套架构能实质性加快开发，因为：

- 领域行为只实现一次、只修一次；
- AI 不用视觉就能测动作核心，同时每个真实 GUI 旅程仍可单独测；
- 移动端和桌面端可以并行开发，各自对着带版本的 fixture 工作；
- 原生界面改版不会重写业务规则；
- 事件重放能复现现场故障；
- 瘦远程客户端传输的数据更少；
- 无障碍、CLI、MCP、自动化和客服工具复用同一套语义；
- 新增一个平台通常只是“投影层 + 一个小能力适配器”。

代价是真实存在的：契约需要治理、事件迁移要小心、离线冲突必须设计、复杂媒体仍
可能要单独通道。回报最先出现在这些产品上：多界面、远程操作、长任务、需要审计、
或者要被 AI 自动化。

## 12. 落地顺序

不要一上来就重写整个产品。

1. 选 3 到 6 个只读或可回滚的动作。
2. 发布它们的输入输出与 State Schema。
3. 加稳定 GUI 绑定和直接的动作测试。
4. 为这些动作追加事件。
5. 只同步这些事件，使用不透明游标。
6. 发布 fixture 集，让任何 Agent 都能离线验证同步规则。
7. 做第二个原生影子。
8. 加第一个需确认的写动作。
9. 度量：重复代码量、测试时长、传输字节、重连正确性、缺陷复现时间。

只有当两个互相独立的产品都跑完这个闭环，影子与同步子规范才应当进入 ActionParity
的规范性正文。
