# Versioning: toolchain, Manifest, and application

ActionParity has three independent version identities. They MUST NOT be inferred
from one another.

| Identity | Current value | Where it appears | What changes it |
| --- | --- | --- | --- |
| Toolchain | `0.7.0` | npm/Cargo package metadata, CLI output, Git tag `v0.7.0` | Generator, validator, verifier, SDKs, adapters, CLI, or packaging |
| Manifest specification | `0.5.0` | `action-parity.json` as `spec_version` | Wire Schema or conformance semantics |
| Application | chosen by the adopter | `application.version` | The application's own release process |

Therefore a Manifest generated by ActionParity `0.7.0` normally contains:

```json
{
  "spec_version": "0.5.0",
  "application": { "version": "2.4.0" }
}
```

This is not a mismatch. The values describe different artifacts.

## Why the public tags jumped from v0.1.0 to v0.6.0

Versions 0.2.0 through 0.5.0 were specification iterations recorded in the
changelog and repository history. They were not published as separately
installable toolchain releases. Version 0.6.0 was the first release containing
the executable Action Registry, generators, verifier, adapters, and packaged
CLI, so the next public Git tag after `v0.1.0` was `v0.6.0`.

That history is semantically valid but easy to misread. We will not create
backdated tags or move the existing `v0.6.0` tag. From `v0.6.0` onward, every
public toolchain release follows the normal sequence and the release notes
state the Manifest specification version separately.

## Release rules

Toolchain releases use Semantic Versioning:

- `0.6.x`: compatible fixes, documentation corrections, packaging fixes, and
  machine-readable metadata;
- `0.7.0`: backward-compatible toolchain capabilities such as a new generator
  or adapter;
- `1.0.0`: the first stable toolchain contract. Before 1.0, any incompatible
  change is called out prominently and receives at least a minor bump.

The Manifest specification has its own sequence:

- a specification patch clarifies wording or fixes a Schema without changing
  conformance meaning;
- a specification minor adds compatible wire fields or pre-1.0 requirements;
- a specification major changes compatibility or normative meaning.

A toolchain release does not change `spec_version` unless its supported wire
contract changes. A specification release does not force an application to
change `application.version`.

## Agent discovery

AI coding tools SHOULD read versions instead of guessing from a Git tag:

```text
action-parity --version --json
```

The stable result envelope distinguishes the identities:

```json
{
  "ok": true,
  "data": {
    "toolchain_version": "0.7.0",
    "manifest_spec_version": "0.5.0",
    "supported_manifest_spec_versions": ["0.5.0"]
  },
  "error": null
}
```

An agent entering an adopted project should then run
`action-parity context . --json` and trust the project's generated Manifest.
It MUST NOT derive the Manifest version from the package version.
