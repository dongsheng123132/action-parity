# 提案：给 Manifest 一个扩展命名空间 —— 否则实现者只能在「藏起来」和「分叉版本号」之间选

> 日期：2026-08-08 · 针对 0.5.0 Manifest schema
> 状态：**提案，未采纳。** 试点侧已按现行 schema 恢复合规（见 §5），代价是一段能力退出了 manifest。
> 提出者：从 U-King 试点一次长期红灯的根因分析里反推出来。

## 0. 一句话

**`additionalProperties: false` + 没有扩展命名空间 = 任何比规范多一点东西的实现，
都无法在合规的前提下把它说出来。**

## 1. 现象：试点长期红灯

U-King 是影核第一个参考实现。它的 `action-parity:verify` 长期是红的：

```
Manifest source is invalid:
/: must NOT have additional properties
/spec_version: must be equal to constant
```

**试点红着，等于规范没有活的验证。** 这比少一个字段严重得多 ——
规范的可信度全部押在「有一个真实项目在持续证明它可用」上。

## 2. 根因不是马虎，是被逼的

查下来是**双向漂移**，而两个方向同源：

| | 试点生成的 | 0.5.0 schema 要求 |
|---|---|---|
| `spec_version` | `0.6.0` | `const: "0.5.0"` |
| 顶层键 | 多一个 `recipes` | `additionalProperties: false` |

试点代码里那行注释把动机写得很清楚：

> `// 0.6.0 = 加了 recipes 段（动作的组合用法）。动作契约本身没变，纯增量。`

它想表达的是一件合理的事：**「我有一段规范没有的东西，是纯增量，动作契约一个字没改。」**
可 0.5.0 的 schema 里**没有任何地方能放这句话**。于是实现者只剩三条路：

1. **藏起来** —— 不写进 manifest。可这正是规范 §3 明令反对的
   （*What conformance forbids is silence*）。
2. **自己改版本号** —— 假装存在一个 0.6.0。试点选了这条，代价就是那盏红灯，
   而且从此**它的 manifest 再也没被任何 schema 校验过**。
3. **不做那个功能** —— 让规范决定产品能有什么。

**三条都是坏的，而规范没给第四条。**

`recipes` 本身是个好例子：它是「几个动作按什么顺序组合能办成一件人说得出口的事」。
清单是 sitemap（我能干什么），配方是 how-to（一件事该按什么顺序做、为什么不能换顺序）。
对 AI 调用方来说，后者往往比前者值钱。规范暂时不想标准化它完全合理 ——
**但「规范不标准化」不该等于「实现者不许有」。**

## 3. 这不是新问题，成熟规范都解决了

| 生态 | 机制 |
|---|---|
| **OpenAPI** | `x-` 规范扩展（schema 里 `patternProperties: {"^x-": {}}`，其余 `additionalProperties: false`）—— 最贴近本场景的先例 |
| **JSON Schema** | 未知关键字默认忽略；词汇表（vocabulary）机制显式声明扩展 |
| **Kubernetes** | `annotations` 是官方指定的「放规范之外的东西」的地方 |
| **JSON:API** | `meta` 成员，任何对象都能挂 |
| **OTLP / OpenTelemetry** | 带命名空间的 attributes |
| **HTTP** | 历史上的 `X-`（RFC 6648 弃用的是「盲目加 X-」，不是扩展本身） |

共同点：**给扩展一个明确、可识别、不与未来标准字段冲突的角落**，
而不是要么全禁、要么全放。

反面教材也要记住：CSS 厂商前缀（`-webkit-`）证明了**扩展一旦被广泛依赖就很难收回**。
所以扩展必须**显式标注为非规范**，并且**不得参与一致性计分**。

## 4. 提案

### 4.1 schema 允许 `x-` 前缀的顶层键与动作字段

```json
{
  "type": "object",
  "additionalProperties": false,
  "patternProperties": { "^x-": true },
  "properties": { "...": "现有字段不变" }
}
```

### 4.2 三条硬约束

1. **`x-` 字段 MUST NOT 影响一致性判定。** 验证器忽略它们，计分不看它们。
   一个实现不能靠加 `x-` 提高任何分数。
2. **`x-` 字段 MUST NOT 与未来标准字段同名。** 标准化某个扩展时，
   标准名不带 `x-`，实现方自行迁移；规范 SHOULD 在 CHANGELOG 里点名。
3. **实现 MUST NOT 因为有扩展而改 `spec_version`。** 版本号描述的是
   **动作契约**遵从哪一版，不是「我这份文件长什么样」。
   这条直接对着本次红灯的成因。

### 4.3 验证器：把扩展**列出来**，而不是忽略掉

一致性报告 SHOULD 有一节列出该 manifest 用了哪些 `x-` 扩展。
这跟规范既有的 §7「排除必须列出」是同一条原则：
**可以有，不可以瞒。** 一个悄悄被忽略的扩展，和一个被藏起来的字段，
对读报告的人是同一种失明。

## 5. 试点侧已经做了什么（不等提案）

不能让规范的缺口继续挂着一盏红灯，所以试点先按**现行 0.5.0** 恢复合规：

- `spec_version` 改回 **`0.5.0`**（说真话：我们的动作契约就是 0.5.0）；
- `recipes` **退出 manifest**。它**一点没丢** —— 真源本来就是 `recipes()`：
  CLI 走 `action recipes --json`，AI 说明书走 `identity::render_recipes(recipe_list())`，
  两条路都不经过 manifest；
- 加了一条单元测试，**顶层键白名单**，把「先越界、再改版本号」这条路堵死：

  > `manifest 多了 0.5.0 schema 不认的顶层键 {...} —— 别改这里的白名单，先去上游要扩展命名空间`

结果：`action-parity:verify` 恢复绿灯（bindings stale=0，conformance 57/57）。

**但这是让步，不是解决。** 现在的状态是：一段对 AI 有价值的结构化数据，
因为规范没有放它的地方，从 manifest 里消失了 —— 它仍然存在，只是
**任何只读 manifest 的消费者再也看不见它**。这正是 §3 说的第 1 条坏路（藏起来），
我们只是把它藏得合规了一点。

`x-recipes` 一旦可用，它就该回到 manifest 里。

## 6. 待拍板

1. 用 `x-` 前缀（OpenAPI 式），还是单独一个 `extensions: {}` 对象（JSON:API 式）？
   前者更省嵌套、先例更硬；后者更容易一眼看出边界。
2. 扩展只开放在顶层，还是动作对象内部也允许？
3. 验证器报告里列扩展，是 MUST 还是 SHOULD？
